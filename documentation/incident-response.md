# Incident Response and Recovery

## Objective

Perform a controlled incident-response exercise against the simulated SSH compromise on the Ubuntu Linux server.

The response followed the incident-response sequence:

1. Identify the compromised SSH persistence state
2. Contain the persistence mechanism
3. Eradicate persistence artifacts
4. Validate audit and SIEM visibility
5. Recover legitimate SSH functionality
6. Perform final system-state validation

## Lab Scope

| System | Address | Role |
|---|---|---|
| Kali | 192.168.50.10 | Attack simulation / validation |
| Ubuntu | 192.168.50.30 | Linux server under investigation |
| Splunk | 192.168.50.40 | SIEM |

Target account:

- `socuser`
- UID/GID: `1001`
- Home directory: `/home/socuser`

This was a controlled lab exercise. The SSH persistence mechanism and sensitive-data activity were simulated using lab-created artifacts.

---

## 1. Pre-Remediation State

The pre-remediation validation confirmed that the `socuser` account existed and that SSH persistence artifacts were present.

The `/home/socuser/.ssh/` directory contained:

- `authorized_keys`
- `soc_lab_key`
- `soc_lab_key.pub`
- SSH host-key files

The `authorized_keys` file contained the lab-generated Ed25519 public key associated with the persistence exercise.

The SSH service was active.

The persistent audit rule was:

```text
-w /home -p wa -k home_changes
````

The temporary `sensitive_data` audit rule was no longer present at this stage.

Evidence:

* `screenshots/39-pre-remediation-state.png`

## 2. Containment

The simulated persistence entry was removed from:

```text
/home/socuser/.ssh/authorized_keys
```

A temporary backup of the file was created as part of the controlled response procedure.

After containment, `authorized_keys` was empty.

Evidence:

* `screenshots/40-ssh-persistence-contained.png`

## 3. Eradication

The persistence artifacts created during the exercise were removed:

```text
/home/socuser/.ssh/soc_lab_key
/home/socuser/.ssh/soc_lab_key.pub
/home/socuser/.ssh/authorized_keys.day7-backup
```

The `authorized_keys` file remained present but empty.

Evidence:

* `screenshots/41-ssh-persistence-eradicated.png`

## 4. Persistence Validation

The final persistence validation confirmed:

```text

```

The SSH service remained active.

This established that removing the simulated persistence mechanism did not require disabling the SSH service itself.

## 9. Incident-Response Findings

### Persistence

The simulated SSH key persistence mechanism was successfully contained and eradicated.

### Audit Visibility

The existing `home_changes` audit rule recorded filesystem activity associated with the persistence artifacts and remediation.

### SIEM Visibility

Splunk received the relevant audit telemetry, allowing the persistence artifacts to be investigated from the SIEM.

### Recovery

Normal password-based SSH access remained functional after remediation.

### Monitoring

The `home_changes` audit rule remained active after remediation.

### Limitations

The `home_changes` rule is broad and records unrelated activity under `/home`. Therefore, audit events must be correlated with paths, timestamps, users, and the incident timeline before being classified as security-relevant.

The Splunk audit data also exposes separate audit records such as PATH and SYSCALL records. These records may need correlation using timestamps and audit event identifiers rather than assuming that every displayed event represents a complete filesystem operation.

The controlled SSH compromise simulation progressed through containment, eradication, validation, and recovery.

The simulated SSH persistence artifacts were removed from the Ubuntu server. Auditd recorded the filesystem activity, Splunk ingested corresponding audit telemetry, and normal password-based SSH access remained available after remediation.
