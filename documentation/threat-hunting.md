# Linux Threat Hunting

## Objective

Perform controlled threat hunting across Linux authentication, auditd, filesystem, and network telemetry to identify activity associated with SSH compromise and post-compromise behavior.

The hunting activity is based only on observed events from the Linux SOC & Splunk lab.

---

## 1. SSH Authentication Hunting

### Failed SSH Authentication

Search for repeated failed SSH authentication:

```spl
index=linux_auth "Failed password"
| stats count as failed_attempts by src_ip user
| where failed_attempts >= 5
````

Observed during the controlled Hydra exercise:

| Source IP     | User    | Failed Attempts |
| ------------- | ------- | --------------: |
| 192.168.50.10 | socuser |               5 |

This identifies repeated authentication failures by source IP and username.

---

## 2. Successful SSH Authentication Hunting

Search for successful password-based SSH authentication:

```spl
index=linux_auth "Accepted password"
| stats count as successful_logins by src_ip user
```

Observed:

| Source IP     | User    | Successful Logins |
| ------------- | ------- | ----------------: |
| 192.168.50.10 | socuser |                 3 |

Successful authentication should be investigated together with surrounding failed authentication activity rather than treated as malicious by itself.

---

## 3. Failed-to-Successful Authentication Correlation

Chronologically review failed and successful authentication:

```spl
index=linux_auth ("Failed password" OR "Accepted password") "socuser"
| sort 0 _time
| table _time src_ip user message
```

This allows the investigator to examine authentication activity involving the same account and source IP.

The Day 5 controlled exercise produced both failed and successful SSH authentication involving:

```text
src_ip = 192.168.50.10
user   = socuser
```

## 4. SSH Persistence Hunting

SSH persistence was simulated by creating an Ed25519 key pair and adding the public key to:

```text
/home/socuser/.ssh/authorized_keys
```

Search the audit index for related SSH key activity:

```spl
index=linux_audit ("authorized_keys" OR "soc_lab_key")
| sort 0 - _time
```

Observed records included:

```text
/home/socuser/.ssh/soc_lab_key
/home/socuser/.ssh/soc_lab_key.pub
/home/socuser/.ssh/authorized_keys
```

The existing audit rule:

```text
-w /home -p wa -k home_changes
```

provided the filesystem telemetry.

## 5. Sensitive File Access Hunting

A synthetic file was created for the investigation:

```text
/srv/company-data/customer-data.txt
```

The file contained only:

```text
LAB CUSTOMER DATA - NOT REAL
```

A temporary audit rule monitored reads:

```text
-w /srv/company-data/customer-data.txt -p r -k sensitive_data
```

Search for the audit key:

```spl
index=linux_audit "sensitive_data"
```

Observed audit information included:

```text
uid=1001
comm="cat"
exe="/usr/bin/cat"
success=yes
key="sensitive_data"
```

Search for the filename:

```spl
index=linux_audit "customer-data.txt"
```

The filename appeared in a separate PATH record.

This demonstrates a useful hunting technique: search both the audit key and the filename because related audit records may be ingested separately.

## 6. Audit Telemetry Hunting

Validate that recent Linux audit telemetry is reaching Splunk:

```spl
index=linux_audit
| sort 0 - _time
| head 20
| table _time host sourcetype source
```

Observed metadata:

```text
host      = LINUX-SRV-01
sourcetype = linux:audit
source    = /var/log/audit/audit.log
```

The audit index contained thousands of events during the investigation period.

---

## 7. Investigating Audit Noise

The broad:

```text
-w /home -p wa -k home_changes
```

rule also recorded activity generated by legitimate investigation and administrative commands.

Examples included filesystem activity associated with commands executed during investigation.

These events were treated as investigation noise rather than automatically classified as attacker activity.

This demonstrates an important hunting principle:

> Audit telemetry must be interpreted in context. A matching audit rule does not by itself establish malicious activity.

## 9. Cross-Source Hunting Workflow

The investigation combined multiple telemetry sources:

```text
Authentication
      |
      v
Account activity
      |
      v
Filesystem changes
      |
      v
Auditd
      |
      v
Splunk
      |
      v
Network traffic
```

A practical hunting sequence is:

1. Identify unusual or repeated SSH authentication.
2. Identify the source IP and target account.
3. Review successful authentication surrounding failed attempts.
4. Investigate SSH persistence files such as `authorized_keys`.
5. Review auditd records for filesystem and process activity.
6. Search for sensitive-file access.
7. Correlate timestamps across authentication, audit, SIEM, and network evidence.
8. Separate investigation-generated noise from the controlled activity being investigated.

---

## 10. Hunting Limitations

The current lab identified several limitations:

* Audit `SYSCALL` and `PATH` records may appear as separate Splunk events.
* The tested audit events did not provide a populated `message` field.
* The broad `home_changes` rule generates legitimate administrative and investigation noise.
* SSH network traffic is encrypted, limiting visibility into commands and credentials.
* The current searches are laboratory hunting queries and are not production-tuned analytics.

---

## 11. Lab Scope

All hunting activity was performed within the isolated Linux SOC & Splunk lab.

The sensitive file contained synthetic data only.

No real customer information was used.
